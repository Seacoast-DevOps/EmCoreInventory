EMCore Inventory
Documentation

From receiving one vial to reviewing its final record. Practical steps for crews, configuration guidance for Service Admins, and an implementation reference for maintainers.

01

Start here

Your account, your service, and one permanent record for each medication item.

EMCore – Inventory helps EMTs, AEMTs, paramedics, and Service Admins receive, locate, check, transfer, use, waste, and review individual medication items. A vial, prefilled syringe, bag, tablet pack, or other presentation is tracked as an individual item, not just a quantity in a bin.

Every item has a permanent eight-character alphanumeric code, such as AB12CD34. Its record follows it through locations, checks, incidents, and witnessed actions.

First launch: Service Admin

  1. If no account exists, enter a service name, your name, a username, a password, and password confirmation. There is no installed default login.
  2. Select Create service & administrator. Existing primary inventory belongs to that first service.
  3. Open Users to create staff accounts. Review starter stock, actual physical inventory, definitions, containers, witness rules, schedules, and policies before operational use.

Returning users

  1. Sign in with your own account.
  2. Check your name and the service selector at the top right. Only active memberships are listed.
  3. Use Home actions or the four bottom buttons. Sign out when finished, especially on shared devices.
Documentation, not a live workspace

The demonstrations in this file do not log in, call the app API, open a camera, or change real inventory. Screenshots use synthetic QA accounts and example stock; your current service may look different.

Content is not a treatment dose

The maximum amount in a definition is labelled medication content per item, not a recommended patient dose. This guide explains the software, not clinical protocols.

Type to filter

Dropdowns filter as you type. Use ↑/↓ and Enter to select; Esc closes the list. Typing alone does not select a required choice.

Editable text, number, date, search, and multiline fields show × when nonempty. Swipe storage areas or use arrows/dots. Containers begin collapsed; only one opens at a time.

A disabled action may be intentional

Account tags, global rules, medication rules, and workflow state determine what you can do. Ask a Service Admin to review access instead of borrowing another login.

03

Receive a batch

Shared lot and expiration; an independent record for every item.

  1. Choose Create Batch / Receive Stock on Home, or Receive drug in Inventory.
  2. Select the standardized drug and concentration. If missing, an authorized user must add a definition in Manage Par Levels.
  3. Enter a whole-number quantity from 1–1,000, a shared Lot number, and a valid shared Expiration date.
  4. Choose generated codes or manual entry. Manual entry needs one different eight-character alphanumeric code per item, separated by spaces, newlines, or commas.
  5. Select Replacement stock when appropriate. Replacement rules can require a witness.
  6. Save. New items appear in Unassigned. Move each item to its actual container afterward.

Permanent codes

Manual codes normalize to uppercase. Codes previously issued in that service database, including used/disposed stock, are rejected. Invalid/duplicate codes reject the batch before partial stock or seal changes.

Historical stock

Blank historical lot/expiration fields mean those details were not recorded; they do not establish that physical medication has no expiration.

04

Locate, move, and inspect stock

A container is a location; an individual record is permanent.

Open Inventory, choose a unit/cabinet in the carousel, and expand a container. Items show presentation, code, status/check state, and recorded lot/expiration. The Unassigned shortcut shows stock awaiting placement. Unassigned stock cannot be checked or used in a physical-use incident until assigned.

Move an item

  1. Select the item’s Move action and a different destination. Same-container moves are excluded and rejected by the API.
  2. If either end is sealed, follow your service’s physical seal procedure. The app asks whether the listed seals were actually broken; Cancel stops the move.
  3. Confirm only after physically breaking the seals. A second user signs in if transfer/seal rules require a witness.
  4. Save and verify the new location. Stock movement invalidates affected container checks.

Inspect the record

Use the record/history icon or enter an eight-character code in Inventory’s lookup. Histories include receipts, transfers, checks, use/waste, seals, corrections, and operator/witness identities. Exhausted used/disposed items leave active inventory but remain accessible by record lookup or QR.

Physical truth

The app records what users report. It cannot sense item presence or a physically broken seal.

05

Perform and resume drug checks

Checkbox changes save immediately; save notes before leaving.

  1. Open Drug Checks or Inventory, choose an area, expand a container, and select Start check.
  2. Find each physical item and select its checkbox. Verification/unverification saves immediately to SQLite.
  3. Enter check notes and choose Save draft before leaving. Resume from that container later.
  4. After every current item is verified, select Complete check. Completed containers hide by default; enable Show completed checks to display them.
  5. Use Check history for earlier sessions. Reset check starts over; Ad hoc check starts an extra session. Neither deletes old records.
StateMeaning / next step

DraftVerification progress or another saved revision exists; resume the check.

Stale draftStock/revision changed since the check began. Reset and verify current contents.

When is a check due?

Drug types and containers default to 24 hours. The shortest positive interval among a container and its current drug types wins. Zero disables that level’s schedule, while another positive interval may still apply. With no positive intervals, checks are manual. Stock and seal changes may invalidate a completion before its due time.

06

Record use, opening, and waste

One incident can contain multiple individually selected items.

  1. Choose Use Medication for a Used Medication entry, or Incident to choose another reason.
  2. Choose a unit/cabinet, expand a container, and select individual items. You can select across areas. Search filters the current area by name, strength, code, or tag.
  3. For Used Medication, enter an incident number. Enter Given and Wasted for each item in the displayed medication unit.
  4. Review the balance. Use remaining amount fills Given with the available quantity and Wasted with zero; review before saving.
  5. Choose Save draft to pause without affecting stock, or Complete incident to commit. Confirm physical seal breaks and obtain witnesses as required.

TRY IT · balance arithmetic

Example medication: 100 training units available. Arithmetic only, not dosing guidance.

The app uses the definition’s unit. It does not automatically convert mg, mcg, mL, or other units.
Draft versus completion

Drafts do not consume medication or break seals. Successful completion updates balances and histories transactionally. Completed incidents become read-only until reopened.

07

Witness using your own account

A second user approves one specific save.

Medication tags can require witnesses for entire/partial use, disposal, opening, replacement, transfer, seal breaking, and resealing. Witness sign-off opens when the operator attempts a witnessed save.

  1. The witness reviews the vial codes, amounts, incident, notes/corrections, destination, and/or seal details.
  2. The witness enters their own username/password and chooses Witness & save. The operator remains signed in.
  3. Invalid credentials/permissions do not commit the action. Cancel stops it without an inventory change.
  4. The successful vial record, applicable incident version, and Logs retain both identities. Corrections require fresh authentication when rules require it.

Who can witness?

  • A different user from the operator.
  • Active membership in the same service.
  • The explicit Can Witness tag, including for Service Admins.
  • No Read Only tag; global and medication witness/view rules must allow it.

The operator does not need Can Witness to request an independent witness. A typed name, user ID, or copied old sign-off cannot authorize a new action.

No password in the record

Credentials are used for that request and removed before draft/history/audit persistence. The record keeps a sign-off reference, user IDs, name/username snapshots, service, method, and time—not the password.

08

Resume, review, and correct incidents

Server-saved work persists; prior completed versions remain available.

  1. Open Incidents on Home or Saved incidents in the editor. Search by incident number or reason.
  2. Open a draft to continue. Browser-local editor state is a convenience; Save draft is the durable server save.
  3. Open a completed incident to review its record and Revision history.
  4. If authorized, choose Reopen incident. Reopening alone changes no balances.
  5. Correct the values, enter a Correction reason, and Save correction. Obtain a new witness when required.
DraftNo stock effect→CompletedBalances applied→ReopenedBalances unchanged→Corrected completionDifference applied
Corrections do not double-count

If the original entry consumed 50 training units and its corrected total is 45, the difference returns 5 units to the balance. Other incidents may have used the vial meanwhile, so an over-allocation is rejected.

Stale revision

Someone else may have saved a newer version. Reload and review the current record before retrying. Do not assume a rejected save committed.

09

Generate and scan QR codes

Go from a label to the existing permanent record.

Create a label

  1. Choose the item’s QR icon in Inventory, or open its record and select Generate / show QR label.
  2. Check the displayed medication, presentation, code, service, and recorded lot/expiration.
  3. Choose Download QR PNG. The PNG contains the QR symbol only; surrounding preview text is not included. Its filename contains the code.
  4. Apply labels according to service procedures without obscuring manufacturer information. No new item is created.

Find a labelled item

  1. Open Scan QR on Home or in Inventory.
  2. Start camera and permit access, choose a QR image, or type/paste the QR text or tracking code.
  3. Review medication, location, status, and balance. Open vial record / QR for the history.
Scanning is lookup, not mutation

A scan does not automatically add an item to an incident, verify a check, transfer stock, or bind an arbitrary external QR. Unknown/wrong-service labels are rejected; external URLs are not followed.

Camera mode prefers the rear camera and stops after detection/navigation. It needs HTTPS or localhost, permission, and a supported camera. Image decoding is local to the browser. Image or typed entry works when a camera is unavailable.

ILLUSTRATIVE QR PAYLOAD
EMCORE:1:primary:EM-0001:AB12CD34

Full QR values match service ID + permanent item ID + code. Bare codes resolve in the current service only. This string is an example, not a newly issued item.

Definitions, medication tags, and par levels

Standardize a drug presentation before receiving individual stock.

Open Manage Par Levels → Add drug, or edit a definition. Catalog access can be delegated through policy.

FieldMeaning
Drug name / classStandardized name and optional organizational class; classes can be created separately or inline.
ConcentrationPositive amount + amount unit + basis, such as per mL or per vial.
Maximum amount per vial / containerTotal labelled content in one item—not a patient-dose limit.
PresentationVial, Ampule, Prefilled syringe, Premixed bag, Tablet, ODT, or Pack.
Check intervalDrug-specific hours; zero disables that level’s schedule.
Medication tagsWitness behavior rules, distinct from user permission tags.
Medication access policiesAdditional view/create/edit/administer/check/transfer/waste/witness restrictions.
Par quantitiesTarget individual-item count per container; blank means no target. Shortages are highlighted.

Amount units: mcg, mg, g, units, mEq, mmol. Bases: mL, vial, ampule, syringe, bag, tablet, pack. Enter the actual supplied label information; the app does not infer a clinical dose or perform unit conversion.

Stocked identities lock

Once stock references a definition, its name, concentration, unit/basis, maximum content, and presentation cannot change. Add a new definition for a different product. Class, tags, policies, schedules, and pars remain configurable.

Medication Tags

Add/edit tags in Medication Tags and attach them to definitions. Witness requirements can cover entire use, partial use, replacement, resealing, disposal, opening, transfer, and seal breaking. Requirements from all attached tags combine.

Classes are organizational, not automatic permissions or clinical scope. Par targets report shortages; they do not order or automatically replace medication.

11

Design storage and manage seals

Areas group containers; containers hold individually coded items.

  1. Open Container / Storage Designer; add a container or edit one.
  2. Set storage area, name, kind, icon, transparency, seal state/number, and check interval. The icon selector previews the choice.
  3. Kinds include Drug box, Cabinet, Narcotic box, and Pelican box. Icons include box, cabinet, truck, lock, and medical.
  4. Sealed containers require a seal number. Changing/removing an existing seal requires physical confirmation. Tags may require witnesses for seal breaking/resealing.
  5. Save. Seal changes affect check freshness; relevant events are recorded against contents.
Unassigned is fixed

Unassigned is not editable in the designer and has no scheduled physical check. Creating/editing a container does not automatically transfer stock into it.

New services start with empty stock plus catalog/container templates. Use Move to place items in their real containers.

12

Manage accounts and personal access

Real accounts identify operators and witnesses.

  1. As a Service Admin in the correct service, open Users → Create user.
  2. Enter a name, application-wide unique username, and initial password. Usernames are 3–80 characters using letters/numbers or . _ @ + -. Passwords are 12–128 characters.
  3. Optionally start from a role template, then review clinician, role, and capability tags. Set active status and save.
  4. Edit user changes details/tags, deactivates membership, or resets a password. Leave New password blank to retain it.
  5. Password reset/deactivation revokes existing sessions. The last active non-read-only Service Admin in a service cannot lose effective admin status.

My Account

Any signed-in user can change their password using the current password, a new password, and confirmation. Other sessions are signed out. There is no email recovery; ask a Service Admin if unable to sign in.

Role templates

Examples: Service Admin — Paramedic; Paramedic — full clinical user; AEMT — clinical / transfer; EMT — drug checks only; EMT — read only; Paramedic — no witness capability. Templates copy tags to a user; editing a template later does not update existing accounts.

Membership limit

The UI creates/edits users in the active service. It has no general invitation workflow for adding an already-existing username to another service. A new service’s creator receives membership there.

13

Maintain services and DEA information

Separate operational inventory and service-specific administration.

As an effective Service Admin, open Services / DEA. Add a service or Edit service / DEA for the selected service. Switch in the header before managing another service you belong to.

InformationStored fields
ServiceName.
RegistrationDEA registrant name, number, expiration date, schedules.
ContactsRegistered address, contact name, email, phone.
NotesAdministrative notes, up to 2,000 characters.

Detailed DEA/contact information is provided only to a non-read-only Service Admin of the selected service. Membership, not admin status alone, controls which services appear.

The DEA number accepts two letters plus seven digits and normalizes to uppercase. Dates must be real calendar dates. These are format checks, not DEA verification. There is no automatic renewal reminder.

Creating another service

The creator gets membership with their current tags. A new service starts with empty stock and starter catalog/container templates, not copied vials, incidents, checks, or operational history.

14

Understand and configure permissions

Account tags, global rules, and medication rules work together.

Tag typeAssigned toPurpose
Account roles/capabilitiesService membershipEMT, AEMT, Paramedic, User, Service Admin, Read Only, Can Check/Transfer/Waste/Witness/Administer/Create/Edit.
Medication tagsDrug definitionChoose which actions need an authenticated witness.

In Access Policies, select a page/function and configure Any/All requirements. Nonempty Any needs at least one match; all All tags must match. Both conditions must pass. Empty lists impose no extra restriction, not deny-all. Medication policies add restrictions beyond global permission.

Read Only blocks ordinary mutation resources. My Account/password and sign-out are still account functions. User/service administration is directly guarded by effective Service Admin status. Service Admin is a default global alternative, not a universal custom-medication-rule bypass. Witnessing still requires Can Witness explicitly.

TRY IT · permission decision
Example user’s tags

Assumes an active membership in the correct service; witness mode also assumes a different user. Demonstrates default global rules plus one medication All-tag rule, not your actual configuration.

Clinical scope is not inferred

Clinician labels and classes are configuration inputs, not automatic authorization of clinical practice. Configure service policies deliberately.

15

Review logs and trace actions

Find the item, operator, and authenticated witness.

Open Logs if allowed. Search by code, lot, medication, user/witness, or action. Filter All logs, Vial / inventory records, Settings changes, or Actions / access decisions.

  • Entries show action, subject, time, and historical acting name/username.
  • Witnessed entries show the authenticated witness. Details includes structured data/sign-off references.
  • Load more retrieves up to 100 additional entries.
  • Logs combines item/settings events, account/service changes, sign-in/out, denials, and witness-required/rejected attempts. Individual histories focus on one item.
  • Migration/legacy attribution stays unchanged. Old name-only witnesses are labelled legacy, not retroactively authenticated.
One save may create several events

An item event and a successful-action log may describe one request; that does not mean medication was deducted twice. Compare item code, incident/revision, amounts, and sign-off ID.

T01

Architecture and implementation

A React client, Node HTTP API, and SQLite databases selected by authenticated service.

React 19Mobile-first client
Bootstrap 6 alpha6.0.0-alpha.1 pinned
Node + SQLiteBuilt-in HTTP / SQLite

Dependencies include React, Vite, Lucide, qrcode, and qr-scanner. The backend uses Node’s built-in HTTP, crypto, and SQLite modules, not Express. The package version is 0.0.0. This guide describes source revision 7202db1, reviewed 13 November 2026.

BrowserReact pages · access context · local editor cache · QR decoding
↓ JSON + session cookie
Node HTTP APIAuthenticate → select service → authorize → validate → transact
Primary SQLiteIdentity + memberships + services + primary inventory
Additional service SQLite filesOne operational inventory database per service

Client navigation uses an in-memory React page stack, not a URL-per-screen router. Mutations return updated snapshots. Inventory hooks poll every 60 seconds while mounted. There is no WebSocket channel, PWA/offline write queue, or automatic cloud backend.

Operational save sequence

  1. Require JSON for POST and reject a supplied foreign Origin host. Parse a JSON object, limited to 65,536 request-text characters.
  2. Authenticate the cookie and active membership; delegate operational access to the selected service database. Identity/user/service routes remain in the primary database.
  3. Build current permissions, strip supplied witness claims, detach transient witness credentials, and authorize the action/medication(s).
  4. Begin an immediate transaction. Validate stock locations, quantities, codes, revisions, and current physical seal confirmations.
  5. When required, authenticate a different eligible witness and persist the sign-off within the operational transaction.
  6. Write item/settings/action events with identity and commit. Errors roll back operational changes. Rejected sign-off/access records and authentication counters may still persist outside the rollback.
Transaction scope

An inventory/check/incident mutation is atomic within the selected operational database. Identity/service management writes separately to the primary database. The application is not a distributed transaction coordinator.

T04

SQLite data model

Twenty-seven tables generated from the current migrations.

The default primary file is server/data/inventory.sqlite; EMCORE_DB can override it. It contains identity data and the primary service’s operational tables. Each additional service’s operational file is service-<UUID>.sqlite, alongside the primary file, initialized on first operational access. Identity remains primary.

T05

State, quantities, and concurrency

The invariants that protect identity and arithmetic.

Permanent identity

Codes are eight uppercase ASCII alphanumeric characters. Internal IDs are separate: legacy EM-… IDs and newer UUIDs both occur. Unique indexes, validation triggers, and the immutable tracking_codes registry prevent code edits/reuse in a service’s inventory database. This is not a global registry across independent services/installations.

ObjectStates / invariant
ItemUnassigned stages new stock. Placement restores available/opened status as appropriate. Partial use can leave opened stock; exhaustion becomes used/disposed according to the incident.
Batch1–1,000 independently coded items share one definition, lot, expiration, batch ID, and receipt time.
Incidentdraft → completed → reopened → completed; saved changes append versions. Drafts do not consume stock.
CorrectionApply new (given + wasted) minus that incident’s old allocation. Validate against current remaining + old allocation.
Checkdraft / complete / superseded. A partial unique index allows one draft per container. Reset/ad hoc preserves superseded sessions.
FreshnessCaptured item set and container stock revision must still match. Stock-affecting changes invalidate old progress/completion.
DefinitionStocked identity fields lock. Item definition snapshots preserve receipt/normalized presentation.
SealConfirmation must match the current seal. Cancelled/failed operational saves do not commit a seal break.

Check due calculation

PSEUDOCODE
effectiveHours = min(positive container interval,
                     positive current-drug intervals)
dueAt = lastCompletedAt + effectiveHours

validCompletion = noDraft
               && stockRevisionMatches
               && itemSetMatches
               && (noDueTime || dueAt > now)

No positive intervals means manual checking with no calculated due time. An untouched draft at revision 1 can still display Not done; progress or another saved revision produces Draft.

Optimistic concurrency and retry

Incident/check writes compare numeric revisions; stale values produce 409. Check saves also compare stock revision and current IDs. A unique client key makes new-incident retries idempotent when supplied. Receipt/transfer do not have a general idempotency key: after ambiguous network failure inspect stock/history before retrying.

T06

Authentication, authorization, and witnesses

Implemented controls and their actual boundaries.

Identity/session controls

  • Passwords: random 16-byte salt, scryptSync with 64-byte output, timingSafeEqual comparison.
  • Sessions: 32 random bytes encoded as 64 hex characters; only SHA-256 token hashes persist in SQLite.
  • Cookie: emcore_session, HttpOnly, SameSite=Strict, Path=/, eight-hour absolute expiry/Max-Age. Secure is set for encrypted requests or EMCORE_SECURE_COOKIE=1.
  • Each request re-reads active membership/tags. Reset/deactivation revokes sessions. Personal password change revokes other sessions and replaces the current one.
  • X-EMCore-Profile no longer selects an authenticated identity.
  • Five failed attempts trigger the remote-address/username lock window; witness keys are separate and survive operational rollback.

Authorization

Global Any/All rules combine with drug Any/All rules. Read Only blocks ordinary non-view resources. Users/services are directly Service Admin guarded; detailed DEA fields are withheld otherwise. Recovery guards retain policy-management access and a final active Service Admin, not universal access through all custom medication rules.

Witness binding

  1. The client receives witnessRequired and shows the pending action summary. It collects credentials in a separate transient dialog.
  2. The server removes submitted witnessCredentials/witness/witnessSignoff/witnessVerified claims from persisted input and keeps a request-scoped resolver.
  3. The witness must be different, active in the service, explicitly Can Witness, not Read Only, and permitted by current global/medication witness/view rules.
  4. An immutable signoff stores its ID, operator/witness IDs, historical witness name/username, service, action, timestamp, password method, and SHA-256 of the reviewed request. Events/incident versions link to it.
  5. Later validation failure rolls back the approval and operational data. There is no reusable approval token; old claims cannot approve corrections.
Not a public-key digital signature

This is account re-authentication and an application audit record, not external timestamping, a regulatory certification, or proof that a physical act occurred. Triggers protect normal signoff SQL updates/deletes; an administrator with database-file control is outside that protection.

Transport/deployment limits

POST requires application/json and rejects a supplied Origin host that differs from Host. There is no separate CSRF token or general CORS API. The entry point binds to loopback. TLS termination, file access controls, durable backup, and deployment review remain maintainer responsibilities. There is no MFA/SSO, email recovery, built-in database-at-rest encryption, or external audit anchoring.

T09

Backup, restore, and deployment

Git preserves source—not operational service data.

Consistent backup

  1. Choose a maintenance window and stop every process writing these databases. Preserve current files before migration or restore.
  2. Copy the primary database and all sibling service-<UUID>.sqlite files together. Retain any required SQLite sidecars as part of the stopped consistent set; do not assume a single live file copy is complete.
  3. Restrict backup access: files contain identities/password hashes, sessions, contacts/DEA details, stock, incidents, and witness metadata.
  4. Restore a matched set into a separate test location first. Start the reviewed application version, check integrity, and verify accounts, service selection, item counts, a historical incident, and a witnessed record before resuming use.

No one-click backup/restore or scheduled backup is implemented. Print/PDF in this document exports documentation, not inventory.

Startup

Migration order: seedInventory → migrateInventory → migrateCatalog → migrateWorkflows → migratePermissions → migrateWitnesses, followed by the primary identity migration. Version markers prevent repeated normalization/stock seeding in an existing installation. The first primary database includes starter/sample stock; additional services start empty. Confirm actual physical stock before use.

Built deployment

npm run build produces frontend assets only. The Node entry point does not serve dist/. A deployment needs a static-file server, same-origin /api reverse proxy, HTTPS, cookie configuration, durable writable data storage, process supervision, and tested backup. Vite development/preview is not a complete production deployment.

The API compares Origin.host with Host. Preserve compatible headers through a reverse proxy; PORT changes also require updating proxy targets. The entry point binds to loopback, so expose it deliberately through a reviewed proxy.

Repository hygiene

server/data/, node_modules, dist, local .env files, SQLite/database copies, and private-key/certificate files are ignored. Commit source and lockfile, not live data or real credentials. Test fixture passwords are synthetic and are not installed operational accounts.
